ARCHITECTURE LAB

Questions under active investigation.

Lightweight design notes—focused on the problem, the architecture and the trade-offs.

Kubernetes database workloads

Problem Stateful workloads carry availability and recovery risk.

Architecture StatefulSets, Longhorn persistence, resource controls and tested recovery.

Trade-offs Operational complexity must justify the resilience gained.

Distributed locking & shared state

Problem Multiple pods can compete for the same work.

Architecture Valkey-backed locks, shared sessions and explicit ownership.

Trade-offs Expiry, failure recovery and lock contention need careful handling.

Connection pooling & queues

Problem Horizontal scale can overwhelm downstream resources.

Architecture Bounded pools and queues smooth database and worker demand.

Trade-offs Backpressure and queue visibility become part of the design.

Stateless services & object storage

Problem Local pod state prevents reliable horizontal scaling.

Architecture Externalise sessions, jobs and objects into shared services.

Trade-offs More network dependencies require stronger observability.

Database optimization

Problem Slow behaviour can come from queries, scans, locks or capacity.

Architecture Metrics, slow-query evidence and targeted query or index changes.

Trade-offs Every optimization must be validated against real workload patterns.

Observability & high availability

Problem Recovery is difficult when system health is opaque.

Architecture Prometheus signals, Grafana views and actionable Alertmanager rules.

Trade-offs Signal quality matters more than collecting every metric.

Application Caching Architecture

Problem
Repeated queries and processing increase database load and response time.
Investigation
Read patterns, invalidation, data ownership and multi-pod coordination.
Solution
Use Valkey for caching while the relational database remains the source of truth.
Impact
Create a path toward locks, sessions, rate limits, queues and shared state.
ValkeyCachingDistributed Locks
